## 实际工具与开发方式

本次在 Windows 本地空目录中，由 Codex 执行开发。使用 Node.js 24、TypeScript、React、Fastify、SQLite、Vitest 和 Playwright。通过 frontend-app-builder 与 imagegen 技能先建立演播厅概念与视觉 token，再按规格实现原生组件。没有使用浏览器与 AI 对话来生成项目，也没有用单个 Prompt 一次生成整个工程。



## 阶段与证据

SDD 阶段先将产品规格拆成状态机、共享类型与数据/API 契约，明确暂停边界、来源标识和异常恢复语义。DDD 阶段将演播厅拆分为 Participants、Transcript、Insights 与页面容器，并使首页与阵容页沿用同一视觉系统。TDD 阶段先添加调度排序、证据校验测试，再围绕持久化检查点扩展失败注入、并发和恢复测试。E2E 阶段让浏览器执行完整用户路径，再校验窄屏布局与页面滚动边界。

每阶段采用实际 Git 提交保留演进，Prompt 指令在开发开始建立的 PROMPTS.md 中按阶段记录。运行时角色 Prompt 单独维护为可审阅代码；密钥不进入仓库，模型日志只包含阶段、耗时、用量与错误类别。

## 代表性问题与解决

**恢复时重复或跳过发言。** 如果只持久化 Transcript，模型在成果分析阶段失败后，继续运行容易直接产生下一条发言，或重复已经完成的发言。实现将剩余队列与待分析消息保存为检查点，和正式发言同事务提交。恢复时先完成待处理成果，再消费剩余队列；测试通过故障注入验证原有消息 ID 不变。

**多个异步意向请求留下过期状态。** 同轮专家并行决定是否参与，若一个请求失败便立即退出，其余请求可能在错误状态之后继续写回“准备发言”。实现使用 Promise.allSettled 等全部请求结束后再处理失败，再统一重置活动。第二位正式发言则串行构建最新上下文，避免两位专家同时回应过期记录。

**构建与可视验收的差异。** 初次前端构建发现无用 CSS import 被打包器当作本地路径，移除后构建通过。自动化 E2E 进一步确认完整流程和手机页签。内置浏览器启动遇到系统沙箱错误时，记录工具限制并采用已安装的 Edge/Playwright 完成验证，不能把“代码可构建”当作“界面已检查”。

## 对工程化 AI 开发的理解

AI 适合加速结构化实现，但工程责任仍在开发者：先固定可验证的接口与状态，再用测试约束行为，并对模型输出做结构、归属和证据检查。测试替身用于重复验证工程链路，真实模型用于验证兼容性和内容质量，两者不能互相替代。对任务中尚未完成的工具要求、真实运行、人工审阅和仓库发布，应直接记录差距，避免交付材料给出虚假的完整性印象。
