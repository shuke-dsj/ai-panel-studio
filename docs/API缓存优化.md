# API缓存优化与质量验收 · 2026-11-18

本轮降低真实API未命中输入Token，不删减话题、角色、原文、共识分歧和受保护证据，不跳过发言/账本审核，不复用旧答案冒充新模型输出。

## 问题与修复

旧请求是“任务专属system + 整块输入JSON”：intent、speech、insights、ledger、review的首条system不同，后续相同历史不能跨任务复用；phase、turns、participation等变化字段又位于messages之前。重试修改最前面的system，日志还丢弃了API返回的缓存计数。

新请求：固定system规则 → user共享材料（资料、按序历史、当前证据及账本）→ 本次任务system与重试约束 → user动态状态和参数。

共享材料每次从当前输入构建，不冻结旧快照。对象键稳定序列化，数组顺序和全部JSON值保留；两个user块合并后与原输入逐值相同，含未知字段和opaque JSON键。当前角色、候选、意向、阶段、计数、关注点、审核反馈放在后面；同一版本的历史、证据和账本可以跨角色、跨任务复用。

任务规则仍为system，引用材料仍为user数据。没有将所有任务规则拼成巨型提示来填充缓存，没有额外预热，也没有串行化专家申请。原API、模型、输出预算、并发、重试、数据库隔离和审核关卡保留；未发送cache_control或prompt_cache_key等未经支持的参数。

`MODEL_REQUEST_LAYOUT=prefix`为真实模式默认值，现有.env无需补填或改Key。`legacy`可用于兼容回退和对照，手动切换后需重启后端。

DeepSeek官方说明：缓存默认开启，匹配已持久化的相同前缀，构建需要时间，服务端不保证100%命中；答案仍重新生成。参考[Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)及[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 真实API对照

最终使用同一组公开合成材料：24条历史，随后追加两条；每种布局5次逻辑调用，包含3次原文保真、1次范围错误审查、1次时间线错误审查。先legacy后prefix，无额外预热，冷请求及所有重试均计入；本轮两组均无格式重试。

未命中输入减少40,083 Token，即**67.53%**。输入总量增加约1.15%，来自分块安全解释和消息边界，没有删除信息来制造节省；这不是账单降幅，输出Token和服务商计费另计。

首次仅共享资料/历史的4次对照也保留：命中2.13%→68.29%，未命中58,939→19,320。扩展证据/账本的中间对照中，新版质量项均过，但旧版将两类错误合报为scope，导致按两个kind计数的假阴性；原passed=false报告保留。最终拆成两个独立错误探针，仍严格核验两类错误。不同轮次调用数不同，不将跨轮百分比差直接解释为算法增益。

模型日志增加discussionId、requestLayout，以及`usage.prompt_cache_hit_tokens`、`usage.prompt_cache_miss_tokens`；兼容`prompt_tokens_details.cached_tokens`。统一输出`cache.status / hitTokens / missTokens / hitRate`。原task、attempt和耗时保留，不记录Key、完整提示或隐藏推理。

## 边界

本轮证明指定合成材料及一场短讨论的表现，不证明任意话题质量完全等价或固定命中率。冷启动、并发冷请求、前提替换、旧证据修订、必要的长上下文裁剪和服务端回收都会降低命中。不能为命中遗漏新发言、冻结旧共识、删掉分歧或跳过审核。客户端没有长期答案缓存，每个新决定仍由真实模型和原证据校验产生。
