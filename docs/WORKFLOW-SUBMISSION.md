# 开发过程与工作流说明

## 如何用 Codex 开发

我把项目拆成规格、组件、核心逻辑和系统验收四块。SDD 阶段先与 Codex 明确讨论状态、数据实体、API 边界和验收场景，并提交共享类型。核心链路使用确定性模型验证调度和归档，再通过 DDD 把圆桌、嘉宾窗、现场记录与成果区域做成独立组件。TDD 迭代把真实运行发现的问题缩成可重复反例，覆盖回放、重启和异常恢复。E2E 用浏览器验证从创建到归档的完整路径，另用真实模型跑短场，逐条核对原话和数据库。提交历史保留每次变更的实际顺序。开发工具为 Codex，DeepSeek 是产品运行时的模型服务。题面指定的 Claude Code + DeepSeek V4 Pro 开发流程没有实际记录。

## 三个典型问题

**运行失败后重复发言。** 初期如果只有 Transcript，成果提取失败后很难判断是否应重放发言。通过故障注入复现后，把剩余队列、待分析消息和正式发言放进同一提交边界，恢复时先补未完成的成果步骤，再验证消息 ID 与序号。

**多方引用容易变成夸大的共识。** 两位专家可能支持不同子句，也可能已撤回旧立场。先保留逐字原文、作者和序号，再用语义审核逐条核对共同支持的最小条款以及反对是否仍有效。总结按核验后的账本装配，外部批准另列待确认。

**压缩和缓存可能损伤承接。** 逐任务重复传角色会增加输入，粗略摘要又可能吃掉关键条件。调整为共享前缀、追加历史和精简角色引用，同时保护边界、条件原句与未决议题。用小样本比较未命中 Token 与原文保真，再跑同题回归，分别报告请求量变化和缓存效果。

## 对工程化 AI 开发的理解

Codex 可以加速实现与试错，工程判断要落在可追溯契约、测试和真实证据上。对状态与引用用代码保证，对观点归因做语义审核，最后单独检查体验和模型输出。预算耗尽、待外部验证以及暂未复现的质量问题，应和成功结果一起记录，便于后来者按同一标准复核。
