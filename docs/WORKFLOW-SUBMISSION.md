# 开发过程与工作流说明

## 如何用 Codex 开发

我使用 Codex 开发，把项目拆成规格、组件、核心逻辑和系统验收四块。SDD 阶段先明确讨论状态、数据实体、API 边界和验收场景，并提交共享类型。核心链路使用确定性模型验证调度和归档，再通过 DDD 把圆桌、嘉宾窗、现场记录与成果区域做成独立组件。TDD 迭代把真实运行发现的问题缩成可重复反例，覆盖回放、重启和异常恢复。E2E 用浏览器验证从创建到归档的完整路径，另用 DeepSeek 运行真实短场，逐条核对原话和数据库。提交历史保留每次变更的实际顺序。

## 三个典型问题

**运行失败后重复发言。** 初期如果只有 Transcript，成果提取失败后很难判断是否应重放发言。通过故障注入复现后，把剩余队列、待分析消息和正式发言放进同一提交边界，恢复时先补未完成的成果步骤，再验证消息 ID 与序号。

**多方引用容易变成夸大的共识。** 两位专家可能支持不同子句，也可能已撤回旧立场。先保留逐字原文、作者和序号，再用语义审核逐条核对共同支持的最小条款以及反对是否仍有效。总结按核验后的账本装配，外部批准另列待确认。

**压缩和缓存可能损伤承接。** 逐任务重复传角色会增加输入，粗略摘要又可能吃掉关键条件。调整为共享前缀、追加历史和精简角色引用，同时保护边界、条件原句与未决议题。用小样本比较未命中 Token 与原文保真，再跑同题回归，分别报告请求量变化和缓存效果。

**恢复时重复或跳过发言。** 如果只持久化 Transcript，模型在成果分析阶段失败后，继续运行容易直接产生下一条发言，或重复已经完成的发言。实现将剩余队列与待分析消息保存为检查点，和正式发言同事务提交。恢复时先完成待处理成果，再消费剩余队列；测试通过故障注入验证原有消息 ID 不变。

**多个异步意向请求留下过期状态。** 同轮专家并行决定是否参与，若一个请求失败便立即退出，其余请求可能在错误状态之后继续写回“准备发言”。实现使用 Promise.allSettled 等全部请求结束后再处理失败，再统一重置活动。第二位正式发言则串行构建最新上下文，避免两位专家同时回应过期记录。

**构建与可视验收的差异。** 初次前端构建发现无用 CSS import 被打包器当作本地路径，移除后构建通过。自动化 E2E 进一步确认完整流程和手机页签。内置浏览器启动遇到系统沙箱错误时，记录工具限制并采用已安装的 Edge/Playwright 完成验证，不能把“代码可构建”当作“界面已检查”。

## 对工程化 AI 开发的理解

Codex 可以加速实现与试错，工程判断要落在可追溯契约、测试和真实证据上。对状态与引用用代码保证，对观点归因做语义审核，最后单独检查体验和模型输出。预算耗尽、待外部验证以及暂未复现的质量问题，应和成功结果一起记录，便于后来者按同一标准复核。
